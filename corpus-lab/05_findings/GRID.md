## What was actually measured

Two corpora, two tests each.

**The trees.** `harness/corpus_15000` is the tree built to resemble the target: 15,010
files, PDF-heavy, **no `.git` and no `.gitignore` at any depth** (checked, zero hits).
`ra-ship` is a git repository whose `.gitignore` excludes every document directory and
where 213,032 of 217,681 files are venv and model-cache noise. **ra-ship is a fixture.
The harness is the one that speaks to the problem.**

**The tests.** *Canaries*: 18 phrases planted in the harness (13 in ra-ship), each in a
known file; the session is given the exact string and asked which file holds it. This
measures whether a tool can find something you can already quote. *Questions*: the
frozen 20 from `question_sample.json`, scored against `answer_key.json` on which
evidence files the session actually reached. This measures the real job.

Three stacks completed both tests on the harness. Three did not run, each for a measured
reason given in the table's footnotes.

## How to read the table

`canary recall` is **answer recall** — the answer named enough of the path to *address*
the file (full relative path, or last two segments). Night 1's scorer accepted a bare
filename over 8 characters, so any answer mentioning any README scored as finding
`02_Source_Documents_Read_Only/README.md`. That loophole never fired on pass 1 (every
night-1 hit matched on full path) but would have on pass 2, whose targets have far more
generic names.

`retrieval` is the stricter question of whether the session actually *opened* the file.
**It is not comparable across stacks.** `files_opened[]` is reconstructed from tool-call
*inputs*, so a path appearing only in a tool *result* — normal for an index stack
answering from snippets — is invisible to it. A large gap between answer recall and
retrieval means the stack is answering from snippets rather than from the document.

`cost` always carries an explicit **n-of-m**. A timed-out session reports no cost and
drops out of the sum, so a stack that flails more looks cheaper. **Two totals with
different n are not comparable.**

`excluded-by-design` is its own column. Two canaries are structurally unreachable: one
under `site-packages` (the indexer excludes dependency directories deliberately — grep
can reach it, an index cannot) and one inside a ZIP (the indexer does not descend into
archives, and grep cannot read a compressed member either, so **no stack here can reach
it**). Folding these into the headline would score a design decision as a failure.

## Per stack — what it did on vague questions

**S0 — stock Claude Code (`Grep`, `Glob`, `Read`, `Bash`).** On vague questions it
wanders. Across 20 questions it issued 200 Bash, 145 Read, 80 Glob and 44 Grep calls, and
also burned calls on `Agent` (11), `ScheduleWakeup`, `SendMessage`, `ListAgents` and
`Monitor` — it began spawning subagents and scheduling wakeups instead of reading
documents. That flailing is why it cost **$12.54**, roughly five times any other stack.
It reached 0.167 mean recall with 12 of 20 questions touching none of their evidence.
Paradoxically it made the *most* evidence contact of the three (4 of 17 questions),
because wandering broadly beats querying a ranker that returns the wrong thing.
*Condition: holds on a tree where built-in search is not crippled — i.e. no `.gitignore`
over the documents, which is the target's situation.*

**S1 — policy only (CLAUDE.md naming `corpus_search.py`; nothing enforced).** On vague
questions it does exactly what it is told, and that does not help. Adoption was total —
`corpus_search` used in **38 of 38** sessions — and the tool mix collapsed: Grep to 0,
Read to 0, Glob 80→6. Cost fell to **$2.89**. Recall moved to 0.176, inside noise of S0's
0.167. It opened a correct evidence file on **0 of 17** questions. The index answers
confidently from snippets that are not the right snippets.

**S2 — index plus a PreToolUse hook denying Grep/Glob/Bash-crawls.** Behaviourally almost
identical to S1, because S1's agent had already stopped using Grep voluntarily. 21 tool
calls against S1's 25, $2.68 against $2.89, recall 0.118 against 0.176, and the same
**0 of 17** evidence contact. On vague questions the hook changes nothing except removing
the fallback that let S0 stumble onto evidence.

**S3 — FTS5 + local embeddings (LanceDB, fastembed `bge-small-en-v1.5`).** Not built.
Measured at **8.2 pages/s** on CPU against 614,150 ra-ship pages and 1,206,260 harness
pages — a 20.8-hour build for the smaller of the two, with no GPU. This is the only stack
in the list that attacks the failure diagnosed below, and it is the one that could not be
built on this machine.

**S4 — pdf-mcp.** Failed its install gate twice over. `pdf_corpus_warm` and
`pdf_corpus_search` accept neither a directory nor a glob, so a caller must enumerate all
9,942 PDFs explicitly — which the S4 hook forbids the agent from doing, so the front door
cannot be opened from inside a session. And warming five small PDFs (32 KB–1.6 MB) took
415 s and returned `docs:[]` with three still unprocessed: ~200 s per small PDF, ~23 days
for the rung. `pytesseract` is a dependency and the rung holds 1,211 image-only PDFs, so
OCR is the likely cause.

**S5 — Recoll.** No headless install path exists: absent from PATH and Program Files,
absent from winget and msstore, and the vendor's Windows page carries no `.exe`, `.msi`
or `.msix` link — the only linked downloads directory holds GPL source tarballs.
Distribution is interactive, which the spec rules dead. Nothing was downloaded.

## S1 versus S2 — did telling work, or did it need forcing?

**Telling worked completely, and forcing added nothing measurable.**

A plain instruction in `CLAUDE.md` moved adoption from **0 of 38 sessions to 38 of 38**.
The hook in S2 then enforced a behaviour the agent had already adopted. Across the two,
canary recall is identical (17/17), evidence contact is identical (0 of 17), cost differs
by 7% and tool calls by four. S2's question recall reads lower (0.118 vs 0.176), but on
n=20 that gap is not safely outside sampling noise and **I am not claiming S2 is worse.**

The one real difference is that S2 removes a fallback. S0, with no index and no
restrictions, made the most evidence contact of the three precisely by ignoring rankers
and crawling. S2 forecloses that. On this evidence the hook's cost is not that it
degrades results, but that it buys nothing over telling while removing an escape hatch.

*Condition: one model (claude-sonnet-5), one prompt shape, 38 sessions per stack. A
different model, or one under heavier task pressure, may not comply as readily — the
round-two concern that motivated the hook is not disproven in general, only unobserved
here.*

## Why recall is stuck at ~0.15 regardless of stack

Diagnosed from data already on disk — no sessions, no cost. Three places the failure
could live:

**A. Ingestion — not the problem.** All **64 of 64** evidence files referenced by the 20
questions are present in the index with status `indexed`.

**B. Lexical ranking — this is the failure.** For the 17 questions whose evidence is
fully indexed, running the question's own content words as a BM25 query returns the
correct evidence file in the top 50 hits **zero times**. Not once.

**B2. And it is ranking, not vocabulary.** The evidence files *do* contain the question's
words — mean **38.9%** of the question's content words appear in the evidence file,
median 33.3%, and only 1 of 27 sampled files contains none. The words are present, and
BM25 still ranks thousands of the other 1.2 million pages above the right one.

**C. The agents corroborate it.** S1 and S2, which route every question through the index,
opened a correct evidence file on **0 of 17** questions. S0, which wanders instead of
searching, managed **4 of 17**. Worse tooling, better evidence contact — which only makes
sense if the ranker is the bottleneck.

**Consequence.** S4 and S5 are both lexical (pdfplumber text search; Xapian BM25) and
share the failing component, so neither would have moved this number. That is now
evidence rather than an assumption. Directions that attack ranking rather than swapping
the engine — shrinking the candidate set before ranking using structure or metadata,
reranking a large top-k, or indexing at a coarser unit than a single page so each unit
carries more signal — were not in the spec's stack list and remain unmeasured.

*Caveat, stated plainly: the BM25 probe in B used an OR of up to 12 content words, which
is a cruder query than an agent would write. It is a proxy. Finding C is not a proxy — it
is what real sessions actually did — and the two agree.*

## A ceiling nobody's stack can clear

Of the harness's 15,010 files, **1,211 are image-only PDFs with no text layer** — 8% of
the tree that no text index and no grep can reach without OCR. A further 18 are encrypted
and 14 fail the parser. This hole is larger than every difference between stacks measured
here. *Condition: the tree contains scanned documents. The target is described as
PDF-heavy, so this very likely transfers and should be checked against the real folder
before any stack is chosen.*

## Fixture-specific — does not transfer

Findings whose enabling condition is **absent** on the target (plain folder tree, no git,
~100 folders and ~10k files, PDF-heavy, Windows, terminal Claude Code). Nothing here may
appear in the headline or in a recommendation.

**1. The `.gitignore` root cause — night 1's entire thesis.** ra-ship's `.gitignore` hides
every document directory, so gitignore-aware search sees 495 of 217,527 files and `Grep`
returns "No files found" for material that is present. *Condition: the tree is a git repo
with a `.gitignore` covering the documents.* **Checked against the target-shaped tree:
the harness has no `.git` and no `.gitignore` at any depth.** The direct measurement:
stock Claude Code found **15 of 17** canaries on the harness versus **4 of 12** on
ra-ship — same stack, same scorer, same night. On a plain folder, `grep` and
`grep --no-ignore` are the same command and this finding describes nothing.

**2. The venv/model-cache bulk.** 213,032 of ra-ship's 217,681 files are dependency
material — 97.9% of that tree is noise no researcher put there. The harness walk found
15,010 discovered, 15,010 candidates, **0 excluded**. *Condition: the tree contains Python
venvs and model caches.* So ra-ship's "3,872 indexed files" is not the corpus, it is the
1.8% left after the noise filter — and the site-packages excluded-by-design row exists
only because of this, and is expected to be empty on the target.

**3. The `claude.cmd` newline bug.** `claude.cmd` is a cmd.exe wrapper whose `%*`
truncates at the first newline in an argument, so a multi-line prompt silently loses
`--output-format stream-json` and the session returns prose with exit 0 and empty stderr.
*Condition: Windows, Claude Code driven as a subprocess through the npm `.cmd` shim,
prompt containing a newline.* Sir drives Claude Code interactively and never hits this.
It is an **instrument** bug — but it invalidated every harness cell night 1 produced,
which is why it is recorded rather than quietly fixed.

**4. The deny-rule, transcript and memory work.** `Read(**/…)` patterns failing open, the
`.claude/projects` transcript route, the memory-dir channel. These are properties of
running a blind measurement, not of retrieval. They matter for trusting these numbers,
and for anyone building a rig like this. They say nothing about whether an index helps
sir find a table.

## What I'd look at first

1. **Ranking, not the engine.** B2 shows the right words are in the right files and BM25
   still buries them under 1.2M pages; swapping one lexical engine for another cannot fix
   that, and two such swaps already failed for unrelated reasons.
2. **Count the scanned PDFs in the real folder.** 8% of the harness is image-only and
   unreachable by any stack here — if the real tree is similar, that hole outranks every
   stack choice on this page.
3. **The absence failure is not a retrieval problem.** 0 of 3 in all three stacks: when
   the honest answer was "not in the corpus", every stack invented one instead.
