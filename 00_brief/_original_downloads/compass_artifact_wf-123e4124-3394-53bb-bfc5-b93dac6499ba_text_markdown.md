# Why Your Agent Goes Blind Deep in the Tree — and How to Fix It

## TL;DR
- **Your framing is half right and half wrong.** The "silently stops seeing things" failure is TWO problems stacked: (1) a real, currently-shipping Claude Code bug — silent microcompaction that deletes earlier tool results with no warning (GitHub issue #42542, regression since v2.1.89) — and (2) a deeper architectural mismatch: your tree is mostly PDFs, and Claude Code's core search (Grep/ripgrep) skips binary files by default, so the agent literally cannot see inside your PDFs via its main tool. It is **not** "the tree got too big for search." It's "the agent was never reading most of your files, and context compaction quietly threw away what little it did read."
- **The single highest-leverage fix is a persistent local index over the tree** — a semantic + full-text index exposed to the agent as an MCP tool — so "a thing buried deep" becomes a query, not a directory walk. Best installable options today: **LEANN** (local, ~5%-of-raw-data index, PDF/file RAG, has an MCP server), or a **paperless-ngx / DEVONthink** layer for the document-management side. For the provenance problem ("this CSV came from that PDF page"), nothing auto-solves it — you record it explicitly with sidecar metadata (Frictionless `sources` field) or a manifest, plus DataLad if you want true lineage.
- **Do NOT reach for GraphRAG/knowledge graphs first** — for "which PDF did this number come from," a graph is overkill and expensive to maintain. Grep-first works for code because code is text; your corpus is not, so you need an extraction + index layer underneath the agent, plus a few CLAUDE.md/AGENTS.md "map" files. Full rank order is in Recommendations.

## Key Findings

### 1. The silent-failure is partly a plain bug you can mitigate today
- **Claude Code microcompaction (issue #42542, open, labeled `bug`/`has repro`).** Since ~v2.1.89/2.1.90, tool-result content from earlier in a session is silently replaced with `[Old tool result content cleared]`. No "Compacting…" notice, no PreToolUse/PostToolUse hook fires. Three mechanisms live in `src/services/compact/`: time-based microcompact (`microCompact.ts:422`), cached microcompact (`microCompact.ts:305`, deletes from server cache), and session-memory compact (`sessionMemoryCompact.ts:57`, ~40k-token keep window). The reporter saw ~80k tokens on a 1M window with early results already gone, and the agent then "makes confident statements from internalised summaries because the source material was silently stripped." Last-working version cited: **v2.1.81**. Critically: `DISABLE_AUTO_COMPACT=true` does NOT stop microcompact; `DISABLE_COMPACT=true` also kills manual `/compact`. Behavior is gated by server-side GrowthBook flags, so it can change with no CLI update or changelog entry. **Confidence: high** (primary source, reproducible, from Claude Code's own decompiled source references).
- **This is exactly your symptom:** "answers from whatever subset it happened to open, stops connecting across branches, gets worse as the tree grows." Bigger tree → more tool calls → microcompact fires sooner → earlier reads evicted. It has "happened on four or five separate projects" because it's session-mechanics, not project-specific.
- **Grep skips binary files by default.** ripgrep (which powers both Claude Code's Grep and Glob) removes binary files: per its own guide, "binary files (like PDFs or images) are typically not things you want to search." Even `-a/--text` won't cleanly search a PDF because the text isn't contiguous UTF-8; you need a preprocessor (`--pre pdftotext`) or rga. On a PDF-heavy tree, the agent's primary discovery tool is **blind to most of your content**. **Confidence: high.**
- **Grep truncation is flagged, not silent — but Glob's ignore behavior can hide files.** Grep/Glob default to a 100-file cap and set a `truncated` flag telling the model to narrow. That part is honest. But Glob does NOT respect `.gitignore` by default while Grep DOES (asymmetry that surprises people), and there are open bugs where the built-in Explore subagent ignores `.gitignore` and CLAUDE.md (issue #26286). The agent SDK also crashes (exit code 1) when Grep exceeds ~100K matches (claude-agent-sdk-typescript issue #72, observed at 106,850 matches). **Confidence: high.**
- **Read tool truncates large files at 2000 lines silently.** A 100k-line log or a big CSV is cut at line 2000 with no error — the agent reasons over the head of the file as if it were the whole thing. Directly relevant to your extracted CSV tables. **Confidence: high.**

### 2. The real problem statement (what's actually wrong)
Your framing ("past a certain tree size the agent stops seeing things") points at search scale. The actual causes, in order of impact:
1. **Context eviction** (microcompact) throws away tool results mid-session — a Claude Code behavior/bug, not a search-scale limit.
2. **The corpus is not text.** PDFs/DOCX/scanned tables are invisible to grep. This is why it "stops connecting across branches" — it never ingested most branches to begin with.
3. **No persistent index.** Every session re-discovers the tree from scratch through a keyhole. No artifact knows where things are.
4. **No provenance layer.** Nothing on disk records that `extractions/run-2026-02-03/x.csv` came from `sources/pbs/…​.pdf` p.42, so the agent can't traverse a link that doesn't exist.

So: it's a **persistent-index + extraction problem first, a context-management problem second, and only incidentally a prompting problem.** Better prompting will not fix a tree the agent can't read.

### 3. Indexing / retrieval layers you can install today
- **LEANN** (`github.com/yichuan-w/LEANN`, UC Berkeley SkyLab). Local ANN vector index that recomputes embeddings on the fly instead of storing them. Per Wang et al., "LEANN: A Low-Storage Vector Index," arXiv:2506.08276: it "reduces index size to under 5% of the original raw data, achieving up to 50 times smaller storage than standard indexes, while maintaining 90% top-3 recall in under 2 seconds" — e.g. a dataset whose standard HNSW index would be ~188GB collapses to a few GB. Runs on a laptop, no cloud. Its README explicitly targets "semantic search your file system, emails, PDFs" and notes "Claude Code only supports basic grep-style keyword search." Has an MCP server. **Best single fit for the stated goal.** Setup: `uv pip install leann`, build an index, expose via MCP. Fails on: large corpora need rebuild management; on-the-fly recompute adds query latency. **Confidence: high on fit; medium on effort (≈ a day to wire).**
- **Vector DBs for a local corpus:** **LanceDB** (embedded, disk-based Lance columnar format, scales past RAM, best local-first), **Chroma** (simplest API, in-memory backed by persistent storage, comfortable to a few million chunks on one 4–8GB VPS), **Qdrant** (Rust, best filtered-query performance, ~27k stars). All have MCP servers. For a single-researcher tree, use LanceDB or Chroma **embedded** — no server to run. **Confidence: high.**
- **Full-text / hybrid:** **SQLite FTS5** (zero-infra, ships with sqlite — the cheapest durable index), Meilisearch/Typesense (typo-tolerant, need a server), and **rga (ripgrep-all)** — the cheapest immediate win: `rga` searches inside PDFs, Office docs, zip, epub, subtitles by shelling out to pdftotext/pandoc. Point the agent at `rga` via Bash and it can suddenly grep your PDFs. **Confidence: high; rga is the fastest thing to try.**
- **PDF/table extraction (you need this regardless of index choice):** In 2026 the three live tools are **Docling** (IBM, MIT license, CPU-viable, best for RAG, ~v2.111; TableFormer >91% TEDS on FinTabNet in ACCURATE mode), **Marker** (Datalab, fastest at scale, ~v1.10.2, but GPL-3.0 code + a RAIL-M weight license that restricts commercial use above a revenue threshold), and **MinerU** (OpenDataLab, accuracy leader especially on complex tables/CJK, ~v3.4.3). For Pakistan Bureau of Statistics yearbook tables, MinerU or Docling ACCURATE mode. PDF-Extract-Kit is effectively frozen (last substantive release v1.0, Oct 2024) — use as a component library, not a product. **Confidence: high.**
- **RAG/document frameworks (turnkey):** **Khoj** (`github.com/khoj-ai/khoj`, ~36k stars, AGPL-3.0, actively maintained, latest 2.0.0-beta.28 published 26 Mar 2026; indexes PDF/markdown/Word/Notion, has Obsidian/Emacs/desktop/phone clients, self-hostable, works with local LLMs via Ollama) is the closest "personal second brain over your files" with semantic search. **Onyx** (formerly Danswer) is heavier/enterprise (40+ connectors, Docker self-host). **Confidence: high on maintenance status.**

### 4. Agent-side architecture
- **An MCP index server is the right shape.** Put the index behind an MCP tool the agent calls with a keyword or natural-language query; it returns file paths + snippets. This is precisely "mention a thing at root, agent goes straight to it." Options: LEANN MCP, Chroma/Qdrant/LanceDB MCP, `zilliztech/claude-context` (semantic search MCP — code-focused but the pattern generalizes; there's a fully-local fork `FarhanAliRaza/claude-context-local` using EmbeddingGemma, no API cost), or a small custom FTS5 MCP. **Confidence: high.**
- **Grep-first vs embed-first, honestly.** Boris Cherny (creator of Claude Code, Anthropic) on the Latent Space podcast, May 2025: "We tried very early versions of Claude that actually used RAG… Eventually, we landed on just agentic search… it outperformed everything. By a lot. And this was surprising," adding "this was just vibes, so internal vibes. There's some internal benchmarks also, but mostly vibes." **That result is for CODE** — text, exact identifiers, changing constantly (so an index goes stale). Your corpus is the opposite: PDFs (not greppable), stable (statistical yearbooks don't change), and you ask semantic questions ("auto-financing share of CPI"). The counter-evidence for documents: on FinanceBench, an agentic keyword-search approach beat traditional RAG by only ~6 percentage points on answer correctness (30.40% vs 24.24%) in one test — and a separate AAAI-2026 Amazon Science measurement put agentic keyword search at ~94.5% of RAG faithfulness with no vector store — i.e. the two are close on documents, and grep's edge does not transfer when the files aren't text. **For your use case, embed + FTS underneath the agent is correct.** **Confidence: high.**
- **Subagents / librarian pattern.** Claude Code supports parallel Task/subagents, each with its own context window, and (since v2.1.172) nested subagents up to 5 levels deep; the Task tool caps at ~10 concurrent. The useful pattern for you: a **"librarian" subagent that owns the index** and answers path queries, plus **map-reduce subagents over file batches** for cross-branch questions (each returns findings, the main agent merges). This directly satisfies "spawns subagents, each knows where to go." Split by **concept, not directory** — feature/concept-based splitting handles cross-branch dependencies that directory-based splitting misses. Caveat: subagents multiply token cost; set `CLAUDE_CODE_SUBAGENT_MODEL` to a cheaper model (e.g. Sonnet/Haiku for search). **Confidence: high on mechanism; medium on how much it helps without an index underneath.**
- **CLAUDE.md / AGENTS.md as the map.** A short root CLAUDE.md plus per-branch AGENTS.md/INDEX.md files telling the agent what lives where and how extractions map to sources. Keep them SHORT: Gloaguen, Mündler, Müller, Raychev & Vechev (ETH Zurich SRI Lab + LogicStar.ai), "Evaluating AGENTS.md," arXiv:2602.11988 (13 Feb 2026), found LLM-generated context files reduced resolution rates by 0.5% on SWE-bench Lite and 2% on their 138-task AGENTBENCH "while increasing inference cost by over 20% on average." Human-written, non-obvious maps win; auto-generated ones that duplicate discoverable info hurt. Note: after microcompaction, path-scoped CLAUDE.md influence is lost until a file in that directory is touched again. AGENTS.md is the cross-tool standard (Codex, Cursor, Copilot, Aider, etc.); Claude Code reads CLAUDE.md and can `@AGENTS.md`-import it. **Confidence: high.**

### 5. How people with huge document trees actually solved it
- **DEVONthink** (Mac): researchers with decades of PDFs use its "See Also"/"Classify" AI to surface related documents across the whole database — exactly the cross-branch relatedness you want. DEVONthink 4 (2026 public beta) added AI chat over the DB; one reviewer runs ~18,000 items. Files stay in original format on disk. Mac-only, paid. **Confidence: high.**
- **Journalists / discovery sets:** ICIJ **Datashare** (open source, powered the Panama/Pandora Papers — 100M+ files, self-hostable, OCR + entity extraction) and OCCRP **Aleph** (400M+ docs/entities, cross-references the same entity across datasets, Docker self-host). These are the proven "millions of heterogeneous documents, find the needle AND see connections" tools; Aleph's entity cross-referencing is the closest existing thing to "this name/number appears across these files." Both are Elasticsearch-based and heavier to run. **Confidence: high.**
- **paperless-ngx:** great up to ~tens of thousands of docs; the maintainers state it targets home users and warn it "will be unusable well before the 5/600K mark." One public-administration install runs ~107,006 docs on 24-core/64GB hardware; another reports ~350k with tuning. Fix slow operations by setting `PAPERLESS_FILENAME_FORMAT` with `doc_pk | int // 100` bucketing (took one user from 2 min to 0.5s per patch). Good as the OCR + tag + full-text layer over `sources/`. **Confidence: high.**

### 6. Knowledge graph / relationship layers — mostly overkill here
GraphRAG (Microsoft) builds an entity graph + community summaries. It is expensive: per KET-RAG authors (arXiv:2502.09304) and Microsoft's own repo, indexing a single 5GB legal-case dataset with GPT-4o-mini cost **~$33,000**; Microsoft Research states LazyGraphRAG's "data indexing costs are identical to vector RAG and 0.1% of the costs of full GraphRAG." LightRAG/Fast GraphRAG cut cost similarly. Graphiti/Cognee are temporal agent-memory graphs. **For "which PDF did this CSV number come from," a knowledge graph is the wrong tool** — that's a provenance edge you record explicitly, not something worth reconstructing via lossy, re-indexing-heavy LLM entity extraction. A graph earns its keep for "what themes recur across 5,000 documents," which is not your question. **Confidence: medium-high.**

### 7. The provenance problem — the part no tool auto-solves
You want: "this CSV came from that PDF page, and this draft claim depends on both." Options, cheapest first:
- **Sidecar metadata / Frictionless Data Resource.** Each extracted resource gets a descriptor with a `path` (the CSV) and an optional **`sources`** array; per the Frictionless spec, "Each Source object MUST have a title and MAY have `path` and/or `email` properties" — so you record the origin PDF (page number in the title, URL/path in `path`) right next to the CSV. Machine-queryable, plain JSON/YAML, no infra. Spec: `framework.frictionlessdata.io/docs/framework/resource.html`. **Best fit.**
- **YAML frontmatter convention** in your notes/extractions: a `source:` / `source_page:` / `derived_from:` field pointing at the PDF path. Trivial to grep, trivial for the agent to read. Pair with a README/INDEX.md per extraction run.
- **DataLad** (git + git-annex) for true lineage: `datalad run` wraps the extraction command so `git log` / `datalad rerun` can reconstruct "how did this file come to be" across the project's life, and `git annex whereis` records where a source was obtained. Heavier; best if you want reproducibility, not just a pointer. **DVC** is the ML-flavored equivalent. **Confidence: high these work; medium on adoption effort.**

### 8. Memory MCP servers (persistent cross-session knowledge)
- **Basic Memory** (`github.com/basicmachines-co/basic-memory`, ~3.6k stars, AGPL-3.0, actively maintained — 1,700+ commits, CHANGELOG v0.18→v0.20, 2026 activity). Local-first: writes notes as **plain Markdown on disk + a SQLite index**, with wiki-style relations (`- relates_to [[Coffee Bean Origins]]`) forming a traversable graph. Install `uv tool install basic-memory`; add to Claude Code with `claude mcp add basic-memory -- uvx basic-memory mcp`. Strong fit for persisting "what I learned about this tree" across sessions AND recording relations between notes and sources. **Confidence: high.**
- **mem0** (`github.com/mem0ai/mem0`, ~56–61k stars, Apache-2.0, very active, npm `mem0ai` v3.1.8). Agent memory layer; **OpenMemory MCP** adds persistent memory to Claude/Cursor (the old `mem0-mcp` repo was archived 24 Mar 2026 and folded into the monorepo's `openmemory/`). Runs fully local only if you swap in Ollama; defaults to OpenAI. More "agent remembers user facts" than "index my document tree" — secondary for your use case. **Confidence: high on facts, medium on fit.**

## Details — how the pieces combine (the stack to actually build)
1. **Extract once:** run MinerU or Docling over `sources/**` → produce markdown/JSON sidecars alongside each PDF (same basename). Now the content is text.
2. **Index:** build a LEANN (or LanceDB) semantic index + a SQLite FTS5 keyword index over the extracted text AND your existing md/csv/docx.
3. **Expose as MCP:** the agent queries the index and gets back exact paths + snippets. "The auto-financing number from the 2021 policy" → three files, instantly, no directory walk.
4. **Provenance sidecars:** every extraction run writes a Frictionless `sources` entry (or `source:`/`source_page:` frontmatter) back to the origin PDF + page. Draft claims cite those pointers.
5. **Maps:** short root CLAUDE.md + per-project AGENTS.md naming the index tool and the provenance convention.
6. **Mitigate the bug:** run `/compact` manually at natural boundaries; keep sessions scoped per-project; don't trust the 1M window to hold earlier reads; watch the token counter (a sudden 180k→12k drop = a compaction event); pin to a Claude Code version at/after the fix once Anthropic ships one (track #42542).

## Recommendations (ranked by whether they hit the goal: mention a buried thing → agent goes straight to it → no silent misses)
1. **Install rga today** (`cargo install ripgrep_all`, or brew/apt). One command and the agent can grep inside PDFs/DOCX via Bash — immediate ~50% of the value, zero architecture. **Do this first.**
2. **Extract + index.** MinerU/Docling → LEANN or LanceDB + FTS5 → MCP tool. This is THE fix that turns "buried thing" into "query." ~1–2 days to wire. Change course if: extraction table accuracy on your yearbooks is poor → switch MinerU↔Docling ACCURATE mode and spot-check cell values against the source PDF.
3. **Provenance sidecars** (Frictionless `sources`, or YAML `source:`/`source_page:`). Start now, retrofit as you extract. This is the ONLY thing that answers "this number came from that PDF, and this draft claim depends on both."
4. **Mitigate microcompaction now:** manual `/compact`, per-project sessions, token-counter watch. Track issue #42542 for a `--no-microcompact` flag / fix.
5. **Librarian subagent + concept-based map-reduce** for cross-branch questions — but only once the index in step 2 exists (subagents without an index just multiply the same blindness in parallel).
6. **If you'd rather buy than build:** DEVONthink (Mac, decades-of-PDF researchers) or paperless-ngx (self-host, OCR + search) as the document layer; Basic Memory MCP for cross-session knowledge.
7. **Skip GraphRAG/knowledge graphs** unless you develop a genuine "themes across thousands of docs" need. Overkill for provenance.

**Thresholds that change the plan:** if your extracted corpus exceeds ~5M chunks or you add parallel users, move from Chroma/embedded to Qdrant. If you cross ~100k source docs, paperless-ngx will strain — go Datashare/Aleph. If index staleness ever becomes painful (unlikely — your sources rarely change), reconsider grep-first for the text-native parts.

## Caveats & empty searches
- **Prices (PKR at ~PKR 280/USD):** LEANN, LanceDB, Chroma, FTS5, rga, Docling, MinerU, Khoj, paperless-ngx, Datashare, Aleph, Basic Memory, DataLad, DVC — all free/open-source (you pay only self-host compute). **DEVONthink** is paid (one-time license, historically ~USD 99–199 → roughly **PKR 28,000–56,000**; verify current tiers). **Embedding APIs:** OpenAI embeddings scale with corpus size; local embeddings (Ollama / EmbeddingGemma) are free. **Managed vector clouds** (Pinecone/Zilliz) start free then ~USD 70+/mo (~**PKR 19,600+/mo**). mem0 defaults to OpenAI unless you configure Ollama.
- **Version/star figures** are mid-to-late-2026 snapshots and drift; treat stars as rough. mem0's star count varied 56k–61k across sources; Basic Memory has no populated GitHub Releases tab (versioning via CHANGELOG/PyPI).
- **The Anthropic grep-over-RAG claim is explicitly "internal vibes + some benchmarks" (Cherny's own words) and was about code.** Do not over-generalize it to documents — the document-corpus evidence (FinanceBench, AAAI-2026) shows RAG and agentic search roughly tied, and your files aren't greppable anyway.
- **Empty / thin searches (you asked for these explicitly):** my queries for **recoll / DocFetcher** (classic local desktop full-text search, 2026 maintenance status) returned nothing usable before the search budget ran out — status unverified; treat as "exists, maintenance unconfirmed." I did NOT get dedicated results on: **Zotero + better-bibtex at scale**, **Logseq / Tana / org-roam at 50k+ notes**, **Obsidian-vault-at-scale specifics**, **txtai / Marqo / Weaviate-embedded / sqlite-vec / sqlite-vss / DuckDB VSS / Vectorlite / Manticore / Zincsearch / Sonic maintenance status**, **mcp-obsidian / mcp-server-everything-search specifics**, **Letta/MemGPT / Zep specifics**, or concrete field examples for **RO-Crate / Dublin Core / schema.org sidecars** (only Frictionless was confirmed with an exact field). These are gaps, not dead ends — each is worth one follow-up search. My web-search budget capped at 18 calls, so §8 and the provenance field were closed via a focused subagent rather than direct search.
