# Round Two: Sub-Document Addressing, Series Continuity, Coverage Accounting, and the Claude Code Build Shape

**Currency note:** USD→PKR is ~277–279 as of this window (Xe quoted 277.36 on Sep 1 2026; Trading Economics cited the SBP interbank rate at 279.05 on Mar 30 2026). PKR figures below use ~278 but treat that as a band, not a fixed peg. The tooling here is overwhelmingly free/open-source, so the real cost is your time, not license fees.

## TL;DR
- **The build shape is decided: a local MCP server that returns page/table-scoped citations, fronted by a PreToolUse hook that denies Grep/Glob and redirects the model to it.** The named, installable off-the-shelf starting point is `pdf-mcp` (MIT, active, `pip install pdf-mcp`, `claude mcp add`), which already does hybrid search + selective page reads + per-table bbox coordinates across a whole folder. The hook-redirect pattern is proven in the wild (Beacon plugin, ContextStream).
- **The same-series-across-years problem is genuinely unsolved off the shelf — nobody has harmonized PBS/SBP/Economic Survey into continuous series, and there is no non-FRED vintage-tracking library.** The correct answer is a hand-rolled crosswalk YAML keyed by a canonical series ID with per-year source pointers (file + page + table + bbox), optionally declared in MetricFlow (Apache-2.0 since Oct 14 2025). Column-matching tools (Splink, dedupe) help at the margin; the academic table-annotation tools (Sherlock/Sato/Doduo) are research code, not installable libraries.
- **All four Claude Code bug claims check out as real and current** — #16043, #12534, #42542, and the Read 2000-line truncation (documented behavior; issues #6910/#28783) — but with one important correction: #12534 is the *VS Code extension*, not the terminal CLI. The user's contradiction is also resolved in his favor: the risk is the working tree churning, not the PDFs changing, so identity must be content-hash-based, not path-based.

### 1. Sub-document addressing (page / section / table as a citable unit)

**The off-the-shelf winner: `pdf-mcp` (jztan/pdf-mcp).** MIT-licensed, `pip install pdf-mcp`, one-line install into Claude Code (`claude mcp add pdf-mcp -- pdf-mcp`). It is an MCP server built for exactly this: hybrid BM25+semantic search (Reciprocal Rank Fusion) over a PDF or a whole folder, returns ranked hits with **document + page provenance** and paragraph excerpts, and — crucially — `pdf_read_pages` and `pdf_search` return **tables and images each with source `bbox` + `clip` coordinates**. It has corpus tools (`pdf_corpus_warm`, `pdf_corpus_overview`, `pdf_corpus_search`) that triage a folder and search across all documents at once, a persistent SQLite cache, OCR via Tesseract for scanned pages, chart-data extraction as `(x,y)` tables, and — unusually relevant for government PDFs — hidden-text / content-trust flagging (it flags text a human can't see so the agent treats it as untrusted rather than vetted). Its own benchmark blog reports section-grain search containing the answer in 97% of a 30-query set vs 80% for fixed-width snippets. It's a small project (94 stars, 1 watcher, but actively developed — 1,043 commits, on PyPI with CI) — so treat it as a **reference implementation to fork**, not a dependency to bet the agency on. Confidence: high that it does what's claimed; medium on long-term maintenance given the bus factor.

**The extraction/chunking layer underneath (all confirmed maintained):**
- **Docling `HybridChunker` / `HierarchicalChunker`** (IBM, `docling-core`). The `HierarchicalChunker` makes one chunk per structural element (paragraph, list item, table) with full heading path in metadata; `HybridChunker` adds token-aware split/merge on top for embedding, and can repeat table headers in each chunk for wide tables. The payoff for citations: every chunk carries `chunk.meta.doc_items` back-references, and every `DoclingDocument` element carries `prov` with `page_no` and a `bbox` (e.g. `{"page_no":6,"bbox":{"l":70,"t":875,"r":230,"b":900},"charspan":[0,13]}`) — i.e. you get "file X, page 340, this rectangle" natively. Known failure: the `docling-serve` chunk endpoint (issue #613) returns doc_items as unresolved JSON pointers, so bbox+page are absent inline and you must re-resolve client-side or call convert with `to_formats:["json"]` — a real gotcha if you use the HTTP server rather than the Python library.
- **Chonkie** — library for structure/semantic chunking, actively developed.
- **LlamaIndex** `RecursiveRetriever` + `PandasQueryEngine` / `MarkdownNodeParser` / `SentenceWindowNodeParser` / `AutoMergingRetriever`; **LangChain** ParentDocumentRetriever — all standard, maintained, well-documented. RecursiveRetriever is the canonical pattern for "node summarizes a table, links to a query engine over that table"; LlamaIndex's own PDF-tables example uses Camelot to extract each table into a DataFrame and links a node to it.
- **unstructured.io** chunk-by-title (uses Title elements to define section boundaries so a chunk never spans two sections).

**Table extraction with coordinates preserved:**
- **pdfplumber** (jsvine) — maps every char to an XY coordinate; `page.crop((x0,top,x1,bottom))`, `page.extract_table()`, and `.debug_tablefinder()` visual debugging. Pure-Python deps (pdfminer.six/Pillow/pypdf), no system install. Best for bordered/text-based tables; **does not auto-detect tables** — you feed it the region, which is actually an advantage when you already know page+bbox.
- **Camelot** — `camelot.read_pdf()`, lattice mode (traces drawn gridlines) vs stream mode (whitespace inference); every Table carries `.page` and `._bbox`, exports to CSV/JSON/SQLite/markdown/DataFrame, and a `parsing_report` with an accuracy score (e.g. `{'accuracy':99.02,'whitespace':12.24,'page':1}`) you can threshold on to auto-discard bad tables. Text-based PDFs only (no scans). Known quirk (issue #486): table bbox coordinates don't always line up with the rendered page image.
- **Table Transformer / TableFormer** (microsoft/table-transformer, and Docling's TableFormer) for structure recognition on harder layouts.
- **DuckDB over the extracted CSVs** as the queryable numeric layer — this is the cheap, correct move for "Pakistan's X trajectory": once tables are CSVs, `SELECT …` over them beats embedding numbers.

**Page-level citation / provenance formats (standards, not installs):** PDF fragment identifiers per **RFC 8118** (Hardy, Masinter, Markovic, Johnson, Bailey; March 2017; Informational; obsoletes RFC 3778, now aligned to ISO 32000-2 Annex O) support `#page=340` and `#nameddest=`, with coordinates "in the default user space coordinate system… 1/72 of an inch measured down and to the right from the upper left corner of the page" — the cheapest way to hand back a clickable location. For robust, reflow-surviving anchoring, the **W3C Web Annotation Data Model** with a **TextQuoteSelector** (prefix/exact/suffix) is the hypothesis.is approach and the right model if paths/pages move. Docling's `prov`/`bbox` is the richest machine-readable option. IIIF is overkill unless he's serving page images.

### 2. The same-series-across-years problem (the hard one — he's right that nothing solves it)

**Verdict: there is no off-the-shelf solution, and his instinct to give up looking for one is correct. Build the crosswalk.** The three gaps, confirmed:
1. **No open-source project harmonizes Pakistan statistics into continuous series.** The only named repos are one-shot digitizations — `cerp-analytics/pbs2017` (2017 census tables → CSV) and `colincookman/pakistan_census` — neither is a multi-year series harmonizer. The closest *harmonized* backend is **State Bank of Pakistan's EasyData portal** (easydata.sbp.org.pk, ~8,000+ variables across 90+ datasets, new full-dataset API, launched June 2022) — but it's a proprietary portal you consume, not a library, and it only covers SBP's remit (monetary/external/real-sector/debt/rates), not the full Economic Survey / provincial yearbook granularity.
2. **No non-FRED vintage/point-in-time library exists.** The vintage concept is only packaged around FRED/ALFRED (`fredapi` v0.5.2, May 2024, with `get_series_as_of_date`/`get_series_vintage_dates`; `pyfredapi`), which is useless for Pakistani PDFs. For point-in-time tracking of a Pakistani series you roll your own bitemporal store (a `realtime_start`/`realtime_end` triple per observation — the ALFRED model, copied by hand).
3. **World Bank/IMF SDMX won't save the granular tables.** Pakistan macro aggregates are reachable via `sdmx1` (see below), but province-level yearbook tables like "motor vehicle registrations by province" are not in WDI/IMF SDMX.

**What to actually install / use:**
- **`sdmx1`** (`pip install sdmx1`, repo khaeru/sdmx) — **very actively maintained: v2.27.0, Aug 2026.** Reads SDMX 2.1 and 3.0 from World Bank, IMF, Eurostat, OECD, UN, ~20+ providers; converts to pandas; runs a daily auto-test of every source's REST endpoints. Use it for the internationally-reported Pakistan indicators so you don't re-key those by hand. **Do not** use the older `pandaSDMX` (dr-leo) — no release in 12+ months, Snyk flags it inactive, SDMX 2.1 only, superseded by `sdmx1` (which is a fork of it).
- **MetricFlow** (dbt-labs/metricflow) as the place to *declare the canonical series once* — **dbt Labs open-sourced it under Apache 2.0 on Oct 14 2025 at Coalesce 2025** (per the repo, "Version 0.209.0 and greater is covered by the Apache 2.0 license"; earlier versions were AGPL then BSL). YAML semantic models + metrics, grain-aware, generates SQL. This is the "declare `motor_vehicle_registrations_by_province` once, map many source tables into it" tool. It runs standalone but most of its value assumes dbt; if he's not adopting dbt, **Cube** (API-centric, YAML/JS models) is the comparable alternative. Realistically, for one researcher, a plain YAML crosswalk is lighter than either — but MetricFlow is the named tool if he wants Git-governed, CI-validated definitions.
- **Column-matching (the "are these two columns the same series" sub-problem):** **Splink** (moj-analytical-services/splink, UK Ministry of Justice) is the best-maintained — v4.0.16 (Mar 2026), Splink 5 in dev, ~2.2k stars, probabilistic Fellegi-Sunter linkage over DuckDB, scales to 100M+ rows. **dedupe** (dedupeio/dedupe, v3.0.3, Aug 2024, ~4.16k stars) for active-learning fuzzy matching with human labeling. **recordlinkage** (J535D165, v0.16, 2024 — slowing, last commit ~Feb 2024, approaching stale). **py_entitymatching / Magellan** (v0.4.2, Feb 2024 — effectively dormant ~2.5 yrs, heavy deps incl. PyQt5/XGBoost/Cython; do not adopt). Caveat: all of these do *row-level* entity resolution; you have to reframe "is column A the same variable as column B" as a matching problem, which is awkward. For ten tables it's faster to eyeball.
- **Semantic column-type annotation (Sherlock/Sato/Doduo):** all three are **research code, not installable libraries** — no PyPI packages, pinned to old Python (Doduo pins 3.7.10, ~31 stars; Sherlock is mitmedialab/sherlock-project, install-from-source only; Sato is replication code). No active maintenance. Skip them. There is no clean installable winner here, and SemTab challenge tooling is a collection of per-team research repos, not a tool.

**The cheapest hand-rolled design (recommended):** a `crosswalk.yaml` (or a SQLite table) keyed by a canonical series ID, e.g.:
```yaml
- series_id: motor_vehicle_registrations_by_province
  unit: count
  notes: "Base-year reclassification in FY2016; Balochistan split reporting pre-2010"
  vintages:
    - year: 2019
      source_file: "econ_survey_2018-19.pdf"
      sha256: "…"          # content hash = identity, survives moves
      page: 342
      table: "4.7"
      bbox: [70, 210, 520, 640]
      column_map: {prov: "Province", value: "Registered (No.)"}
    - year: 2020
      source_file: "PBS_yearbook_2020.pdf"
      sha256: "…"
      page: 118
      table: "Table 12"
      bbox: […]
      rebased: true
```
Key the vintage on the **SHA-256/BLAKE3 content hash**, not the path (so a moved/renamed file still resolves). This YAML *is* your series-continuity layer; an MCP tool reads it and returns the right (file, page, table) tuple for any year. This is a weekend of work and it's the only thing that will actually know "these ten differently-named tables are one series." Confidence: high — this is exactly what statistical agencies do internally (SDMX Data Structure Definitions + concordance/crosswalk files); you're doing it in miniature. On splicing discontinuous series: the standard economics moves are base-year rebasing and **chain-linking** (OECD Glossary: "Joining together two indices that overlap in one period by rescaling one of them to make its value equal to that of the other in the same period, thus combining them into single time series"; OECD uses the annual-overlap method) — record the rebasing in the YAML `notes`/`rebased` fields; there is no tool that automates the splice for you, it's a documented judgment call.

### 3. Coverage accounting ("47,203 of 48,100 indexed; here are the 897 that failed and why")

**His observation is correct — most indexers silently swallow failures — but there is one strong off-the-shelf lead: Apache Tika's `tika-eval`.** The `tika-eval-app` module (since Tika 1.15) is built to profile an extraction run and emit exactly this kind of report: it writes results to an H2/SQLite database with per-file outcomes and a **"Tag exceptions by mime"** report (count of files that triggered a parse exception, by MIME type) plus a **"Tag exception details"** report listing *every* file that threw. Tika runs it against ~3 million files in its own regression testing. Caveat from the docs: "it will not scale to 100s of millions of files as it is currently designed" — irrelevant at 48k. This is the closest thing to a drop-in failure manifest. Confidence: high that it produces the report; medium on setup friction (Java, batch config).

**Other partial leads:** unstructured.io and LlamaIndex `SimpleDirectoryReader` have error hooks but default to skip-and-continue; paperless-ngx has a failure/retry queue in its UI; Airflow/Dagster/Prefect give task-level failure records if you wrap each file as a task (heavyweight for one user); Great Expectations / Soda do data-quality reporting but on already-loaded data, not parse failures. None of these gives the clean "897 failed, here's why" table out of the box except tika-eval.

**The cheap wrapper (recommended, ~1 day):** walk → hash → attempt-parse → record outcome to SQLite → report. Named libraries:
- Walk: Python `os.scandir`/`pathlib`, or `rg --files` for speed.
- Hash for identity + change detection: **BLAKE3** (`blake3` — fastest) or **xxhash** (`xxhash` — non-crypto, very fast); SHA-256 if you want a crypto guarantee. For deduping the corpus itself: **fclones** (Rust, fast), **jdupes**, or **czkawka**.
- Attempt-parse with a per-file `try/except` and a timeout; classify the exception into a fixed taxonomy: `corrupt` / `encrypted` / `password_protected` / `image_only_needs_ocr` / `permission_denied` / `unsupported_format` / `too_large` / `timeout`. (image-only = text-layer extraction returns near-zero chars but the page renders; encrypted/password = the PDF library raises a specific decrypt error; corrupt = parser throws on structure.)
- Record `(path, sha256, size, mtime, status, error_class, error_msg, attempted_at)` to SQLite.
- Report = one `SELECT status, count(*) … GROUP BY status` plus the full failure list.
This is strictly better than tika-eval for his purpose because you control the taxonomy and it emits the exact sentence he wants — and it doubles as the content-hash index foundation (see the contradiction section). Confidence: high.

### 4. Omission reporting at query time ("I read 5 of 48,100; here's why I ruled out the rest")

**Be honest: this is the weakest area, and the strong version of what he wants does not exist in any production tool.** No shipping system emits a defensible "I searched N of M documents and ruled out the other M−N because X" trace. What exists is two separable halves, both imperfect:

- **Retrieval-side coverage is tractable and cheap.** Because retrieval scores every candidate (or every candidate in a first-stage recall set), you *can* emit "N candidates scored, top-K read, next-best 20 with their scores and why they fell below threshold." That's an honest, printable omission report at the retrieval layer — and it's a few lines on top of any vector/BM25 store (LanceDB/Chroma/Qdrant/FTS5, all from round one). This is the part worth building. The catch: "ruled out" really means "scored below the cut," not "semantically confirmed irrelevant."
- **Abstention / knowing-it's-not-in-the-corpus is a live research problem, not a solved feature.** State of the art: **semantic entropy** (Farquhar, Kossen, Kuhn, Gal, "Detecting hallucinations in large language models using semantic entropy," *Nature* 630(8017):625–630, 20 June 2024, doi:10.1038/s41586-024-07421-0) detects "a subset of hallucinations—confabulations—which are arbitrary and incorrect generations" by clustering semantically-equivalent samples and measuring meaning-level uncertainty; **Semantic Entropy Probes** (Kossen et al., arXiv:2406.15927) make it cheap. **Conformal abstention** (Abbasi Yadkori et al., Google DeepMind, "Mitigating LLM Hallucinations via Conformal Abstention," arXiv:2405.01563) "reliably bounds the hallucination rate… with rigorous theoretical guarantees" on closed-book open-domain QA. **SelfCheckGPT** for black-box sampling consistency. Evaluation/attribution frameworks worth wiring in as guardrails: **RAGAS** (context precision/recall, faithfulness), **TruLens**, **DeepEval**, **ARES**, **Arize Phoenix**, **LangSmith** tracing. Benchmarks that define "should have abstained": SQuAD 2.0 / QASPER / Natural Questions null answers, **NoMIRACL**, **CRAG**, **RAGTruth**. Even advanced models show concerning hallucination rates — the SeSE framework (Zhao et al., 2025, via arXiv:2601.22290) reports "28% for DeepSeek-V3.1 and 27% for Gemini-2.5-Flash" on its uncertainty setup — so an abstention layer reduces, never eliminates, confident wrong answers.

**Recommendation:** build the retrieval-side coverage report (real, cheap, defensible) and add a RAGAS/Phoenix faithfulness gate; treat semantic-entropy-style abstention as an experimental add-on, not a promise. Confidence: high on the retrieval half, high that the abstention half is not production-ready.

### 5. Delivery mechanism inside Claude Code

For each mechanism, concretely:

**MCP server** — invoked as a tool the model chooses to call; refreshes via its own file watcher or on-call indexing; **does not automatically get in front of Grep/Glob** (the model reaches for built-ins first). This is the right home for the retrieval logic and page-scoped citations (pdf-mcp is exactly this), but it must be paired with a hook to force use. Critical caveat: **issue #33106 — PreToolUse `permissionDecision:"deny"` is NOT enforced for MCP tool calls** (the hook fires, returns deny, MCP tool runs anyway). Deny *is* enforced for built-in tools. So the pattern is: deny the **built-in Grep/Glob**, and let the model fall through to the **MCP** tool — not the reverse.

**Claude Code Skill** — model-invoked when the task matches the skill description; good for "always-on knowledge that semantic search is available" (Beacon ships a semantic-search skill). Skills are better than commands for always-on behavior but still rely on the model choosing them.

**Hooks** — deterministic, fire on lifecycle events, and are the only mechanism that can intercept a tool call *before* it runs. Confirmed capabilities:
- **SessionStart hook** can refresh/rebuild the index with no manual step. **PostToolUse** matched to `Write|Edit|MultiEdit` re-embeds just the changed file (Beacon does this). **UserPromptSubmit** can inject "semantic search is available" context. **PreCompact** can re-inject index status so the model doesn't forget the tool after compaction. Use `async: true` (shipped Jan 2026) for heavy indexing so the session isn't blocked.
- **PreToolUse can block and redirect Grep/Glob.** Return exit code 2, or JSON `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"…"}}`. The reason string is fed back to the model, and you can add `additionalContext` and (since v2.0.10) `updatedInput` to rewrite parameters. PreToolUse fires *before* the permission check, so a deny holds even under `--dangerously-skip-permissions`. Note: it does **not** fire for `@`-referenced files (those are inlined without a tool call) — use a Read deny rule for those.
- File watchers for the non-hook path: **watchexec**, **watchdog** (Python), **fswatch**, **entr**; schedule full rescans with **launchd** (macOS) / **systemd timers**.

**Disabling built-ins:** `settings.json` `permissions.deny: ["Grep","Glob"]`, or `--disallowedTools` CLI flag, or `allowed-tools` frontmatter in slash commands, or agent-level tool restriction in subagent frontmatter. Precedence: deny beats allow at every level; managed-settings.json can't be overridden by `--allowedTools`. Note the docs' hedge: Read deny rules are applied to Grep/Glob/LS only as a **"best-effort attempt."** And a deny rule blocks the built-in tool but **not** `rg`/`find` run via Bash — so also deny `Bash(grep:*)`, `Bash(rg:*)`, `Bash(find:*)` or the model routes around you.

**Real examples of people doing exactly this (not just docs):**
- **Beacon** (github.com/sagarmk/beacon-plugin, MIT) — semantic code search plugin (hybrid vector + BM25, sqlite-vec + FTS5); PreToolUse hook intercepts grep, returns `permissionDecision:"deny"` with `additionalContext` to redirect to its index; PostToolUse re-embeds on edit; PreCompact re-injects status. The author's DEV.to writeup is a step-by-step of the grep-intercept pattern. This is the closest working template.
- **ContextStream** (@contextstream/mcp-server) — ships a PreToolUse hook that blocks Glob/Grep/Search/Explore/Task/EnterPlanMode and redirects to ContextStream search, **but only if the current project is indexed** (graceful fallthrough otherwise). Good design to copy.
- **ck / ck-search** (BeaconBay/ck, `cargo install ck-search`) — local semantic+BM25 grep that runs as an MCP server (`ck --serve`, `claude mcp add ck-search`).
- **grepai** (yoanbernabeu/grepai) — local semantic search, file-watcher auto-index, MCP server; the r/ClaudeAI quote ("took 13% of my max5 plan just to read my codebase") is the exact pain point.
- HN thread (item 47664735) — someone replacing context-stuffing with tree-sitter chunk embeddings in SQLite, storing embeddings on a git orphan branch.

**What broke in practice:** #33106 (deny doesn't apply to MCP tools) is the big one — design around it. #63525 shows built-ins can vanish under `ENABLE_TOOL_SEARCH=1`. #47565 reports the model ignoring custom MCP tools despite CLAUDE.md rules and enforcement hooks — i.e. CLAUDE.md alone is not enough, you need the hard hook. Overly broad PreToolUse matchers add ~80ms/call (measured) — match only `Grep|Glob`.

### The contradiction: index staleness — the user is right

**Adjudication: the user is correct and round one was wrong on this point.** Round one said staleness won't matter because source PDFs rarely change. But the failure mode isn't the PDF content changing — it's the **working tree churning around the files**: moved, reorganized, re-extracted, renamed. A path-keyed index that points at a location that moved is worse than no index, because it fails *silently* and confidently — exactly the class of bug the whole project exists to kill. Path is the wrong primary key.

**The fix: content-addressed identity.** Key the index on a **BLAKE3 (or SHA-256) content hash of the file**, not its path. Then a moved/renamed file keeps its identity, and a genuinely changed file gets a new hash and is flagged for reindex. This is exactly how git-annex/DataLad work (content-addressable store; a moved annexed file's symlink is fixed up by `datalad save`) and how IPFS CIDs work. You don't need to adopt DataLad wholesale — just steal the idea: store `sha256 → (current_path, page/table index, embeddings)` and treat path as a mutable attribute, not identity. Tools that already survive moves this way: **DEVONthink** and **Zotero** track by internal item ID; **recoll** and **Everything** re-scan; **paperless-ngx** hashes documents on import (dedup by checksum).

**Recommended refresh strategy (concrete):**
1. **Identity = content hash.** Every indexed unit is keyed by BLAKE3 of the file; the path is a lookup attribute that can change freely.
2. **SessionStart hook does an incremental reconcile, not a full reindex:** walk the tree, fast-hash files (xxhash on size+mtime suspects first, BLAKE3 only on those that changed), and diff against the index — new hash → index; known hash at new path → just update the path; missing hash → mark stale/removed. At ~48k files this is seconds-to-low-minutes on the fast-hash path, not a full re-embed.
3. **PostToolUse `Write|Edit|MultiEdit`** re-embeds single changed files during a session (Beacon pattern).
4. **A file watcher (watchexec/watchdog)** or a launchd/systemd timer catches out-of-session churn; full re-embed only when the embedding model or chunker changes.
5. **Never trust a path from the index without confirming the hash still resolves** — if it doesn't, that's a coverage-report entry, not a silent miss.
Cost of a full reindex at this scale is dominated by embedding, not walking/hashing; the whole point of content-addressing is that you almost never pay it — you re-embed only genuinely new/changed content.
